# Unified Record Profile • Name Variants • Scheduled Notifications

## 1) Unified Record Profile (يعيد استخدام Entity Resolution)
زر 📚 تحت نتائج البحث (`ent:<id>`) يفتح الملف الموحد: Unified Entity ID • Match status • Match confidence (الاضعف بين الروابط + نسخة المطابق) • الحقول الاساسية • **كل القيم المختلفة** للحقل الواحد (لا اختيار نهائي عند التعارض؛ preferred مجرد ترتيب موثق) • لكل قيمة: الملف، الارشيف الأب، الورقة/الصف، العمود، **وقت الاستيراد** • الاحداث (زيارات/تحاليل/صرف) بمصادرها • الحقول الاضافية • **السجلات الاصلية المرتبطة** (رقم السجل، مصدره، SHA-256 في Source Values) • ادلة المطابقة. 
* كل سطر مقروء من البيانات المستوردة فقط (مفحوص: كل قيمة معروضة موجودة في `record_values`). لا شبكة ولا OSINT (مفحوص: فتح socket يُسقط الاختبار).
* الصلاحية: `search` (لا يوجد row-level ACL في النظام: من يملك search يرى كل الكيانات المفهرسة؛ **لا يوجد نطاق اضيق من ذلك حالياً**). كل فتح ملف يُسجَّل في audit (`entity_profile`). النص الطويل يُقسَّم على رسائل ضمن حد Telegram.

## 2) الأسماء البديلة (Name Variants)
* **لا جدول جديد**: الـvariants هي القيم الخام المخزنة اصلاً ضمن سجلات الكيان؛ الكيان الموحد عرض فوقها (تجنب تكرار البيانات). صيغ الاسم المتوافقة (همزة/تشكيل/اختصار الاسم الاوسط) تُجمع كقيمة واحدة بصيغ متعددة.
* البحث بأي variant موجود يعمل (البحث على الخام ثم تجميع بالكيان) مع التطبيع العربي و fuzzy الحاليين.
* نتيجة البحث توضح **القيمة التي سببت المطابقة** (`«احمد محمد حسن» (variant) [FullName] ← lab.csv / row=1`) مع الملف والصف، وعلامة variant اذا كانت غير القيمة المفضلة او مطابقة تقريبية.
* **لا aliases مخمّنة ولا transliteration تلقائي**: بحث `Ahmad` لا يجد `أحمد` الا اذا كانت الصيغة اللاتينية موجودة فعلاً في ملف مستورد (مفحوص). اسم لاتيني بنفس المعرّف يذهب لـNEEDS_REVIEW ولا يُدمج تلقائياً.

## 3) Scheduled Notifications — **مقيّدة عمداً**
ADMIN فقط (🔔 في لوحة الادارة): مستلمون (IDs) • نوع المحتوى • الجدولة (`every N` ≥5 دقائق، `daily HH:MM`، `weekly D HH:MM`) • الحد الاقصى للعناصر • الصيغة (نص) • تفعيل/تعطيل/حذف/تشغيل الان.
**المحتوى المدعوم (لا يحمل سجلات افراد):**
| النوع | المحتوى | المستلم |
|---|---|---|
| `stats` | احصائيات مجمّعة (اعداد فقط) | يحتاج صلاحية `stats` |
| `ops_summary` | ملخص تشغيلي (مهام، مساحة، ذاكرة، عدادات مراجعة ER) | ADMIN فقط |
| `task_events` | اكتمال Import/Reindex/Export/Matching | USER: مهامه فقط • ADMIN: الكل |
**غير مدعوم عمداً:** Saved Search / نتائج Query / تقارير جاهزة / اي بيانات سجلات تُدفع تلقائياً الى Telegram. هذا قرار متسق مع استبعاد الارسال التلقائي للسجلات؛ تظل النتائج والتقارير متاحة عند الطلب فقط حسب الصلاحية. (محاولة انشاء جدولة بهذه الانواع تُرفض برسالة واضحة ومفحوص أن الكود لا يلمس جداول السجلات.)
**عند كل تنفيذ:** المهمة تعمل كـTask (`notify`) • تُعاد قراءة صلاحية المستلم **الحالية** (مفقود/معطّل/سُحبت صلاحيته ⇒ يُتخطى ويُسجَّل denied) • شرط Force Subscription ينطبق على غير الادمن • audit لكل ارسال/تخطي/فشل • تقسيم الرسائل حسب `TELEGRAM_MESSAGE_LIMIT` • عند فشل الارسال: اعادة محاولة للمستلمين الفاشلين فقط (حتى 3، backoff 60/120/240ث) ثم `failed`، وتظهر كمهمة فاشلة في Tasks. لا ارسال اذا لم يوجد جديد (task_events).
**الحدود:** التوقيت حسب ساعة الجهاز المحلية؛ المجدول thread داخل العملية (يتوقف مع البوت؛ الجدولات الفائتة أثناء الايقاف تُنفَّذ مرة واحدة عند أول tick). ارسال ملفات مجدولة غير مدعوم. لم يُجرَّب على Telegram الحقيقي (NEEDS_TERMUX_TEST).
